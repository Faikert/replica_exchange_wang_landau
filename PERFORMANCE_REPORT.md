# Оценка производительности Wang–Landau

Дата измерений: 15 июля 2026 года.

## Краткий вывод

Оптимизированное инкрементальное обновление реализовано и даёт хорошую скорость для разреженного backend. На 4096 спинах CSR достигает медианы 18.11 млн попыток/с при `cutoff=3.0` и 15.15 млн попыток/с при `cutoff=5.1`, тогда как dense снижается до 0.685 млн попыток/с. Для модели Apamea полный REWL-прогон ускоряется с 1.878 млн попыток/с на одном потоке до 6.239 млн на 12 потоках: ускорение 3.32 раза, эффективность 27.7%.

Основные ограничения производительности:

- **существенное:** dense-обновление имеет `O(N)` работы при каждом принятом flip и быстро упирается в память/кэш;
- **существенное:** построение CSR выполняет полный перебор пар `O(N²)`, хотя последующие flip-обновления имеют `O(z)`;
- **существенное:** инициализация полей для CSR использует двойной цикл по всем `i,j` и линейный поиск в строке CSR, а конструктор walker дополнительно вычисляет поля второй раз через `total_energy`;
- **существенное:** без MPI восемь энергетических окон выполняются последовательно, OpenMP распараллеливает только walkers внутри текущего окна;
- **малое:** интервалы управления и лимиты теперь задаются в MCS, а metadata сохраняет также разрешённые flip-attempts; это делает настройки сопоставимыми между системами разного `N`.

Для производственных расчётов с локальным cutoff следует предпочитать CSR. Dense оправдан для малых систем или физически полного конечного набора пар, но не масштабируется на большие `N`.

## Методика микро-бенчмарка

Использовался штатный `wl_bench`. Геометрия — периодическая плоскость `L×L×1`, поэтому число спинов равно `N=L²`. Для каждого случая выполнялся отдельный прогрев, затем пять измерений:

```powershell
$env:OMP_NUM_THREADS = '1'
wl_bench.exe 16 30000000 dense
wl_bench.exe 32 30000000 dense
wl_bench.exe 64 30000000 dense
wl_bench.exe 16 50000000 csr 3.0
wl_bench.exe 32 50000000 csr 3.0
wl_bench.exe 64 50000000 csr 3.0
wl_bench.exe 16 50000000 csr 5.1
wl_bench.exe 32 50000000 csr 5.1
wl_bench.exe 64 50000000 csr 5.1
```

Таймер внутри `wl_bench` охватывает только Metropolis flip-loop после построения связей и начальных полей. Обновление полей выполняется лишь для принятых flip, поэтому throughput зависит от acceptance rate и не является чистой пропускной способностью операции `add_flip_delta`.

| CSR, cutoff 3.0 | 4096 | 3.604% | 18.109 | 18.017–18.279 |
| CSR, cutoff 5.1 | 256 | 3.014% | 16.200 | 15.397–16.328 |

Наблюдения:

- dense замедляется в 20.3 раза при росте от 256 до 4096 спинов;
- CSR почти сохраняет скорость при росте `N`, поскольку число соседей при фиксированном cutoff остаётся ограниченным;
- на 4096 спинах CSR быстрее dense в 26.4 раза для cutoff 3.0 и в 22.1 раза для cutoff 5.1;
- сравнение dense и CSR не является сравнением идентичной физики: cutoff отбрасывает дальние пары и одновременно меняет acceptance rate.

## Стоимость запуска backend

Для оценки построения геометрии, couplings и начальных полей измерялось wall-time процесса с одной попыткой. Таблица содержит медиану трёх запусков и включает накладные расходы старта процесса.

| Backend | 256 | 1024 | 4096 |
|---|---:|---:|---:|
| dense | 0.012 с | 0.061 с | 0.899 с |
| CSR, cutoff 3.0 | 0.014 с | 0.067 с | 0.878 с |
| CSR, cutoff 5.1 | 0.015 с | 0.088 с | 1.171 с |

И dense, и CSR строятся полным перебором `i<j`, поэтому старт растёт примерно как `O(N²)`. CSR экономит работу только после построения списка. Для коротких задач или часто меняющейся геометрии эта цена заметна.

## OpenMP-масштабирование полного Apamea REWL

Использована реальная геометрия `examples/apamea/apamea_N720.csv`, CSR cutoff 5.1, восемь окон, десять walkers на окно, одинаковые 100 000 попыток на walker и seed-набор для каждого числа потоков. Каждый результат — медиана трёх запусков; wall-time включает построение связей, инициализацию walkers, REWL и запись CSV/JSON.

```powershell
$env:OMP_NUM_THREADS = '<1|2|4|8|12>'
wl_run.exe --config .\examples\apamea\run.ini `
  --seed <фиксированный seed> --max-attempts 100000 `
  --final-factor 1e-300 --output "$env:TEMP\wl-audit-apamea-..."
```

| Потоки | Медиана wall-time | Throughput, млн попыток/с | Ускорение | Эффективность |
|---:|---:|---:|---:|---:|
| 1 | 4.259 с | 1.878 | 1.00× | 100.0% |
| 2 | 2.361 с | 3.389 | 1.80× | 90.2% |
| 4 | 1.530 с | 5.229 | 2.78× | 69.6% |
| 8 | 1.381 с | 5.794 | 3.08× | 38.6% |
| 12 | 1.282 с | 6.239 | 3.32× | 27.7% |

Acceptance составлял около 63.7%. Масштабирование хорошее до двух потоков, приемлемое до четырёх и быстро насыщается после четырёх. Причины видны в структуре `run_rewl`: без MPI окна обрабатываются последовательно, а параллельный участок ограничен walkers текущего окна; присутствуют последовательные проверки flatness, усреднение DOS, обмены и I/O.

## Сложность и память

| Операция | Dense | CSR |
|---|---|---|
| Построение couplings | `O(N²)` | `O(N²)` с фильтрацией cutoff и сортировкой рёбер |
| Память couplings | `8N²` байт | примерно `16Nz + 8(N+1)` байт |
| Начальные поля в текущем коде | `O(N²)` | хуже оптимального `O(Nz)`: двойной цикл и поиск `at(i,j)` |
| `ΔE` | `O(1)` | `O(1)` после вычисления полей |
| Принятый flip | `O(N)` | `O(z)` |

Для 4096 спинов dense-матрица занимает 128 MiB. На квадратной решётке CSR требует примерно 1.78 MiB при `z≈28` (`cutoff=3`) и 5.03 MiB при `z≈80` (`cutoff=5.1`), без учёта capacity/allocator overhead.

Для Apamea независимо подтверждено `N=720`, `z=103.2`: ориентировочная память CSR около 1.14 MiB против 3.96 MiB dense.

Важные детали реализации:

- `CsrCouplings` строит список через перебор всех пар (`src/physics.cpp:197–223`);
- `local_fields` проходит все `j` и вызывает `Couplings::at` (`src/physics.cpp:238–250`); для CSR это не использует естественный проход по соседям;
- конструктор walker сначала вызывает `local_fields`, затем `total_energy`, который снова вычисляет поля (`src/wang_landau.cpp:80–81`);
- OpenMP применяется к walkers (`src/parallel.cpp:129–134`), но не обеспечивает одновременную работу разных окон в serial/OpenMP-режиме.

## Приоритеты оптимизации

1. **Существенное:** реализовать специализированное вычисление начальных полей через последовательный обход CSR-рёбер, не через `N²` вызовов `at`.
2. **Существенное:** вычислять начальную энергию как `0.5 Σσᵢhᵢ` из уже готовых полей, исключив второй расчёт полей.
3. **Существенное:** для больших геометрий строить neighbor list через spatial cells/verlet grid, чтобы уйти от `O(N²)` при фиксированном cutoff.
4. **Существенное:** использовать MPI для одновременной обработки энергетических окон; текущая машина не позволила проверить эту ветвь.
5. **Малое:** для сравнения производительности между размерами публиковать одновременно flips/s и MCS/s; равное число MCS означает разную вычислительную стоимость при разных `N`.
6. **Малое:** расширить benchmark отдельными режимами forced-accepted update, rejected proposal и полного WL step; текущий Metropolis benchmark смешивает стоимость proposal с acceptance rate.

## Ограничения измерений

- CPU affinity, turbo frequency и фоновые процессы Windows не фиксировались.
- Микро-бенчмарк выполнялся на одном потоке и не измеряет MPI.
- Для полного REWL использованы короткие несходившиеся прогоны с фиксированным объёмом работы; они предназначены только для измерения throughput.
- Cutoff 3.0 и 5.1 задают разные физические системы.
- Измерения относятся к GCC 13.2/MinGW на указанном CPU и не переносятся напрямую на кластер или другой компилятор.

## Итоговая оценка

**Производительность CPU-ядра удовлетворительна для CSR и систем с локальным cutoff.** Инкрементальная схема действительно избегает полного пересчёта энергии на каждом шаге. Главные резервы — построение/инициализация CSR и параллелизм по энергетическим окнам. Dense backend корректен как базовая реализация, но при нескольких тысячах спинов становится на порядок медленнее и требует квадратичной памяти.
